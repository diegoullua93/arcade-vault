## Project

Arcade Vault: a retro platform to play games online and compete for the highest scores (README and UI in Spanish). The project follows spec-driven development: every feature has a spec in `specs/NN-slug.md` (01 visual screens, 02 home, 03 about/contact, 04 Supabase, 05 asteroids, 06 leaderboard and `games` table, 07 tetris, 08 arkanoid, 09 serpentina, 10 touch controls, 11 performance, 12 auth) and is implemented on a `spec-NN-slug` branch (`specs/.spec-config.yml`: `AutoCreateBranch: true`).

# Skills

Usa siempre /frontend-design para diseñar la interfaz de usuario

- `/spec` y `/spec-impl` (de `Klerith/fernando-skills`, en `.agents/skills/`): `/spec` redacta un spec en `specs/` a partir de `template.md`; `/spec-impl` lo implementa en su rama.
- `/frontend-design` (de `anthropics/skills`, en `.agents/skills/`, enlazado desde `.claude/skills/`).
- `/add-game <id> [fuente]` (propia, `.claude/skills/add-game/`): para añadir un juego (portado desde `references/` o nuevo) con su leaderboard. Genera el spec en `specs/`, que luego se implementa con `/spec-impl`. Sus `references/` documentan el contrato del motor (`engine-contract.md`) y los puntos de integración (`integration.md`).

- Agente `game-planner` (propio, `.claude/agents/game-planner.md`): decide qué juego encaja como el siguiente según los lineamientos de la plataforma y termina recomendando `/add-game <id>`. Su memoria es `game-suggestions-todo.md` (raíz), donde registra las sugerencias pendientes, aceptadas, descartadas e implementadas. Solo escribe en ese archivo.
- Agente `game-jam` (propio, `.claude/agents/game-jam.md`): recibe un tema, pregunta lo necesario (con `AskUserQuestion` o devolviendo un bloque `## PREGUNTAS PARA EL USUARIO` que el hilo principal le hace al usuario y reenvía al agente) y escribe al menos 2 specs de juegos alternativos inspirados en él en `specs/game-jam/<tema>-<id>.md` (formato de los SPEC 07–09, `Status: draft`, con sección «Preguntas abiertas»). El elegido se mueve a `specs/NN-juego-<id>.md` y se implementa con `/spec-impl`. Solo escribe en `specs/game-jam/`.

- Agente `skin-designer` (propio, `.claude/agents/skin-designer.md`): garantiza que cada juego de `PLAYABLE_GAME_IDS` tenga 3 skins de juego (`neon`, `classic`, `mario`; el de `mario` toma como referencia Serpentina). Audita qué falta, crea la infraestructura (`lib/games/skins.ts`, selector en `game-screen`) si no existe e implementa los skins por juego. Invócalo tras añadir cada juego nuevo (después de `/spec-impl`).

- Agente `mobil-porter` (propio, `.claude/agents/mobil-porter.md`): garantiza que cada juego de `PLAYABLE_GAME_IDS` se vea y funcione en celular según el SPEC 10 (mando táctil, `touchKeys`/`touchRepeat`, layout 390×844 y 360×640, gestos, liberación de teclas). Audita, corrige solo la capa de React/CSS (`components/game/`, `app/globals.css`) y verifica con Playwright en emulación táctil; nunca toca `lib/games/**`. Invócalo tras añadir un juego (después de `/spec-impl` y `skin-designer`) o ante un problema en móvil.

- Agente `security-auditor` (propio, `.claude/agents/security-auditor.md`): audita la seguridad de la base de datos (RLS, políticas, funciones `SECURITY DEFINER`, privilegios, deriva de migraciones) y de la app (Server Actions, `proxy.ts`, `safeNext`, clientes Supabase, secretos, cabeceras, dependencias) contra los SPEC 12 y 13. Solo audita y propone: no cambia código ni base de datos y no crea usuarios de prueba; cada hallazgo que merezca arreglo va a un `/spec`. Su memoria es `security-findings.md` (raíz), donde lleva lo abierto, lo aceptado a propósito (`is_username_available`, contraseñas filtradas) y lo corregido; es el único archivo que escribe. Invócalo tras cambiar el esquema, la autenticación o `saveScore`, y antes de un despliegue.

- `/spec-impl-game <NN-spec>` (propia, `.claude/skills/spec-impl-game/`): implementa un spec de juego de punta a punta encadenando, en orden y nunca en simultáneo, `/spec-impl`, el agente `skin-designer` y el agente `mobil-porter`. Si una fase falla, no ejecuta las siguientes.

Versiones fijadas en `skills-lock.json` (instalación: `npx skills@latest add <repo>`).

## Architecture notes

- App Router only (`app/`); no `pages/`, no `src/`. Path alias `@/*` maps to the repo root. Routes: `/` (home, sections in `components/home/`), `/biblioteca` (library with category filter), `/juegos/[id]` (detail + leaderboard), `/juegos/[id]/jugar` (game player), `/salon` (hall of fame), `/acerca-de` (about + contact form), `/auth` (login/registro) with `/auth/olvide`, `/auth/restablecer`, `/auth/username` and `/auth/callback` (Route Handler), and `/perfil` (protected). Page params use the global `PageProps<"/route">` type.
- `next.config.ts` enables `cacheComponents`, `partialPrefetching`, and `experimental.agentFeedback`. `cacheComponents` changes caching/dynamic-rendering semantics, so consult the docs before fetching data or using request APIs in components. Security headers (SPEC 13): `headers()` in `next.config.ts` sends `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: strict-origin-when-cross-origin` on every route (`/(.*)`); check them on a production build (`npm run build` + `npm run start`). HSTS, Permissions-Policy and CSP are not set. `app/not-found.tsx` is the themed 404 for any unmatched route (reuses `av-hero` and `btn`; returns 404, never redirects), and `redirects()` aliases `/login` → `/auth`.
- Styling: Tailwind v4 wired through Turbopack (a `turbopack.rules` entry in `next.config.ts` runs `@tailwindcss/turbopack` on `*.css`), configured in CSS only (no `tailwind.config`). `app/globals.css` holds the retro theme ported from `references/templates`: tokens on `:root` (`--bg`, `--ink`, `--cyan`, `--magenta`, `--yellow`, `--green`, `--gold`...) exposed as utilities via `@theme inline` (`bg-bg-2`, `text-cyan`, `font-pixel`...), plus most component styles as plain classes (`av-*`, `crt`, `lb-*`...). Dark theme only (`color-scheme: dark`). The root layout loads `Press_Start_2P` and `JetBrains_Mono` via `next/font/google`, uses the global `LayoutProps<"/">` type, and wraps `Nav` + page + `Footer` in `SessionProvider`.
- Auth and session (SPEC 12): Supabase Auth with cookies (`@supabase/ssr`): email + password with email confirmation, and Google (no other providers). `proxy.ts` (Next 16 name for middleware; `lib/supabase/proxy.ts` has `updateSession`, which refreshes the token with `getClaims()`) redirects `/perfil` without a session to `/auth?next=/perfil`, `/auth` with a session to `next` (sanitized with `safeNext` in `lib/auth.ts`, else `/biblioteca`), and sends a session without profile to `/auth/username`; the profile query runs only on `/auth` and `/auth/username`, not on every request. Server Actions are in `app/auth/actions.ts` (`signUp`, `signIn`, `signInWithGoogle`, `requestPasswordReset`, `updatePassword`, `createProfile`, `signOut`; they return `{ ok, error?, field? }`, with a generic message for bad credentials, and build email/OAuth redirect URLs from the `SITE_URL` env var via `lib/site-url.ts`: required in production (without it `requestPasswordReset`/`signUp`/`signInWithGoogle` answer `failed` and `/auth/callback` redirects to `/auth?error=callback` with a relative `Location`), optional in development, where the request `Host` is used; `X-Forwarded-Host` is never trusted). `app/auth/callback/route.ts` exchanges the PKCE `code` and redirects to `next`, or to `/auth/username` if there is no profile. Validation limits live in `lib/auth.ts` (`AUTH_LIMITS`: username 3–10 chars `A-Z0-9_` stored uppercase, password 8–72). `SessionProvider` is a Client Component that reads the session with the browser client (`onAuthStateChange`) and the username from `profiles`; `user` is `null` on the server, during hydration and while the profile loads. `useSession()` exposes `user` (`{ name }`), `signOut` and `refresh()`; forms call `refresh()` after login or after creating the profile, because a Server Action writes the cookies and the browser gets no event. Do not add `router.refresh()` right after `router.push()` in those forms: it produced an intermittent 404 on the `/biblioteca?_rsc` prefetch. Manual Supabase/Google setup (redirect URLs, Google provider, custom SMTP) is documented in SPEC 12.
- Contact form (`/acerca-de`): Client Component `components/about/contact-form.tsx` calls the Server Action `sendContactMessage` (`app/acerca-de/actions.ts`), which validates against `CONTACT_LIMITS` (`lib/contact.ts`), has a `website` honeypot, strips control chars from header fields, and sends via Resend. Needs `RESEND_API_KEY`, `CONTACT_TO_EMAIL`, `CONTACT_FROM_EMAIL` (see `.env.example`).
- Supabase clients live in `lib/supabase/`: `client.ts` (Client Components), `server.ts` (Server Components/Actions/Route Handlers, async, reads cookies) and `anon.ts` (no cookies, for `use cache`). Always call `createClient()` per request; never keep a client in a module-level constant or global. Config comes from `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (see `.env.example`); no secret/service_role key is used.
- Database (Supabase, schema in `supabase/migrations/`, applied with `apply_migration`): `games` (catalog, 8 rows, read-only) and `scores` (public read; insert only for the owner, see below; no UPDATE/DELETE), `profiles` (1:1 with `auth.users`: `username` unique case-insensitively, format `^[A-Z0-9_]{3,10}$`, immutable, readable and insertable only by its owner), plus view `game_stats` (`security_invoker`, `best`/`plays` per game) and functions `get_leaderboard` / `get_player_best` (best score per player name, case-insensitive). RLS is on in the same migration that creates each table. Each score has `user_id` (null on the older rows and the seeds); the insert policy `scores_insert_own` requires the `authenticated` role, `is_seed = false`, `user_id = auth.uid()` and `player_name` equal to the owner's profile username, and the game to have `games.playable = true` (a new game's migration must set it, in sync with `PLAYABLE_GAME_IDS`), so anonymous inserts, name impersonation and marks for non-playable games fail on RLS. Table grants are minimal (SPEC 14): `anon` only `SELECT` on `games`, `scores` and `game_stats`; `authenticated` also `SELECT` on `profiles`, `INSERT (id, username)` on `profiles` and `INSERT (game_id, player_name, score, user_id)` on `scores` (`id`, `created_at` and `is_seed` are set by the DB), no `UPDATE`/`DELETE`/`TRUNCATE`; a new table must grant explicitly what the app needs. Triggers: `profiles_check_username_history` (BEFORE INSERT, rejects a username present in `scores.player_name` of someone else's rows, `23505 username_taken`) and `scores_rate_limit` (BEFORE INSERT, more than 10 marks per `user_id` in 60 s raises `rate_limited`). `rls_auto_enable()` and the `ensure_rls` event trigger are versioned in `20261114120400_version_rls_auto_enable.sql`. For production, `supabase/prod/` holds the scripts to build an empty database (`build-schema.sh` regenerates `01-schema.sql`; see `docs/produccion.md`). The leaderboard functions still group by player name. The trigger `on_auth_user_created` creates the profile from `raw_user_meta_data.username` at sign-up (Google users have none and pick it in `/auth/username`), and `is_username_available(p_username)` (SECURITY DEFINER with `search_path = ''`, callable by `anon` and `authenticated`; the advisor lints 0028/0029 warn about it, intentionally: it must run before sign-up, and the project uses no `service_role`) rejects names already in `profiles` or in `scores.player_name`, so a new user cannot inherit an old name's marks. `rls_auto_enable()` is the function of the `ensure_rls` event trigger (enables RLS on new `public` tables); its `EXECUTE` is revoked from `PUBLIC`/`anon`/`authenticated` (SPEC 13 migration), so it is not callable via `/rest/v1/rpc`. Accepted advisor warnings: the two on `is_username_available` and `auth_leaked_password_protection` (out of SPEC 13). Test users can be created with `execute_sql` on `auth.users` (confirmed, empty token columns) because the confirmation email cannot be opened from Playwright; delete them afterwards. Types are generated in `lib/supabase/database.types.ts` (regenerate after schema changes). The 50 `is_seed` rows cover 5 games (the 4 non-playable ones, `gloton`, `invasores`, `ranaria` and `duelo-pixel`, plus `tetris`, which kept the seeds of its former `caida` row); `asteroids`, `arkanoid` and `serpentina` only have real scores (`arkanoid` is the former `bloque-buster`, renamed by migration; the seeds of `arkanoid` and `serpentina` were deleted by migration because they were unreachable or would not be reached in normal play). The build needs `NEXT_PUBLIC_SUPABASE_*` because `generateStaticParams` reads `games`.
- Reads live in `lib/queries/`: `games.ts` (`getGames`/`getGame` are `use cache` with `cacheTag("games")` and long `cacheLife`; `getGamesWithStats` adds dynamic `game_stats`) and `scores.ts` (`getLeaderboard`, dynamic, never cached; dates formatted on the server in UTC/`es-ES`). Anything inside `use cache` must use `createAnonClient()` from `lib/supabase/anon.ts`; dynamic reads use the cookie-aware `server.ts` client under `<Suspense>`. Pages pass data to Client Components (`Library`, `HallOfFame`, `GameCard`) via props; "Tu mejor marca" is the only client-side query (`get_player_best` with the browser client, by session name). Shared game types (`Game`, `GameWithStats`, `CATS`, `formatPlays`, `PLAYABLE_GAME_IDS`) are in `lib/games.ts`.
- Saving scores: `GameScreen` calls the Server Action `saveScore` (`app/juegos/[id]/jugar/actions.ts`) once per game when `onHudChange` reports `gameover`, only with a session and score > 0 (guests see a link to `/auth`). `saveScore` takes only `gameId` and `score`: the owner and name come from the server session (`auth.getUser()` + `profiles`), and `unauthenticated` (no session or no profile) makes `GameScreen` show the guest link. It validates against `lib/leaderboard.ts` limits and `PLAYABLE_GAME_IDS`, inserts with `user_id`, reads the rank with `get_player_best`, and `revalidatePath`s `/salon` and `/juegos/{id}`. It is not a security barrier (the DB `CHECK`s and RLS are). The status (`GUARDANDO` / `GUARDADO #N` / `ERROR` + `REINTENTAR`) is React in the CRT bottom bar; the engine is untouched.
- Game engines live in `lib/games/` (`types.ts` shared; one folder per game: `asteroids/`, `tetris/`, `arkanoid/`, `serpentina/`, each split into `constants`, `entities`, `utils`, `game` and optionally `levels`/`draw`). An engine is plain TypeScript with no React/Next imports: `createXGame(canvas, callbacks)` keeps all state in its closure and returns `{ pause, resume, restart, destroy }`; `destroy()` must cancel rAF and remove every listener. `components/game/game-screen.tsx` (Client Component) creates the engine in `useEffect`, returns `destroy` as cleanup, and mirrors the HUD via `onHudChange`. Per-game settings live in `GAMES_CONFIG` (game-screen): `create`, internal canvas `width`/`height` (asteroids, arkanoid and serpentina 800×600, tetris 300×600), `showLives` (false for tetris and serpentina, whose engines emit `lives: 0`) and `showNext`. With `showNext` the frame switches to the vertical `crt--side` layout and the engine reports the next piece through the optional `onNextChange` callback, which React draws on a second 120×120 canvas (the engine still receives a single canvas). Binary assets live in `public/games/<id>/` and the engine loads them itself (arkanoid's `classic` skin loads its spritesheet before the loop starts and aborts if destroyed meanwhile). A game without a "win" status emits `gameover` when completed (arkanoid draws a victory overlay, serpentina one for a full board), so the score is saved like any other game. Serpentina uses no assets: everything is drawn on the canvas, with the static background (sky, hills, checkerboard) cached once in an offscreen canvas, and it moves on a 40×30 grid of 20 px cells by accumulating `dt` into fixed steps. To add a game (or use `/add-game`): new engine folder, register it in `GAMES_CONFIG` and in `PLAYABLE_GAME_IDS` (`lib/games.ts`), and make sure it has a row in `games` (insert or rename via migration).
- Skins: every playable game must offer 3 views (`SkinId` in `lib/games/skins.ts`: `neon` default, `classic`, `mario`; `SKINS` holds the labels). The engine takes `createXGame(canvas, callbacks, options?: { skin })` and the skin is fixed at creation: switching = `destroy()` + new engine (new game). Logic and rendering are split: simulation, hitboxes, speeds and scoring are identical in every skin; only the drawing layer changes, in `lib/games/<id>/skins/{neon,classic,mario}.ts` (each a factory returning the same draw functions, typed in `skins/types.ts`) plus `skins/index.ts` with `getSkin(id)` (a fresh instance per engine, so caches and effects are not shared). Each skin caches its static background in an offscreen canvas and draws its own PAUSA/GAME OVER overlays (neon `Press Start 2P`, classic a 3×5 bitmap font drawn with `fillRect`, mario the rounded `FONT_FAMILY`). The `mario` look follows Serpentina's palette and techniques without third-party characters or assets. `GAMES_CONFIG.skins` enables the selector (`NEÓN · CLÁSICO · MARIO BROS`; in the side panel for `crt--side`, else in the HUD actions), persisted in `localStorage` key `av_skin` via `useSkin()` (`components/game/use-skin.ts`, `useSyncExternalStore`, server snapshot `neon`); with a game in progress (score > 0, not gameover) it pauses and asks for confirmation inline. The CRT frame gets `crt--classic`/`crt--mario` (compatible with `crt--side`). Done: tetris (its next-piece canvas uses `drawNextPiece` with the same skin) and arkanoid (its spritesheet is now the `classic` skin; skins expose `load(onReady)` and the engine starts the loop when the skin is ready, so only `classic` fetches the image). The 3×5 bitmap font is shared in `lib/games/bitmap-font.ts`. Asteroids and serpentina still have only their original look (`skins: false`; serpentina's current look is its future `mario` skin). New games ship their base skin through `/add-game`; the `skin-designer` agent adds the other two.
- Touch controls (SPEC 10): `components/game/touch-controls.tsx` is a single pad for every game (D-pad, A, B, PAUSA/SEGUIR, and REINICIAR visible only in `gameover`), mounted by `GameScreen` below the CRT frame. It never touches the engines: `use-touch-keys.ts` dispatches synthetic `KeyboardEvent`s on `window` (↑↓←→ = `Arrow*`, A = `Space`, B = `KeyX`, PAUSA = `KeyP`, REINICIAR = `Space`), with multitouch via `PointerEvent` + `setPointerCapture` (one `pointerId` per button). `GAMES_CONFIG` gets `touchKeys` (controls with a function in that game; the rest render dimmed and send nothing) and `touchRepeat` (D-pad autorepeat, 170 ms delay then 50 ms, only for tetris, because its engine acts on every `keydown`; serpentina must not repeat or it fills its turn queue). The pad is `display: none` and only shows under `@media (hover: none) and (pointer: coarse)` (pure CSS, no JS detection). Everything is released (`keyup`) on `pointerup`/`pointercancel`/`lostpointercapture`, window `blur`, tab hidden, `gameover` and unmount. On narrow touch screens (`max-width: 640px`) a compact block in `globals.css` makes nav + HUD + frame + pad fit in 390×844 without page scroll (it hides the site footer and sizes tetris' board with `100dvh`), `.av-player` has `touch-action: manipulation`, the canvas and pad `touch-action: none`, and `GameScreen` adds `av-playing` to `<html>` (`overscroll-behavior-y: contain`) only while mounted. The pad has one look for every skin. Not done: gestures on the canvas, landscape layout, per-game pads. For testing on a phone over the LAN, `next.config.ts` reads `allowedDevOrigins` from the `ALLOWED_DEV_ORIGINS` env var (comma-separated).
- Performance (SPEC 11): engines follow `.claude/skills/add-game/references/performance.md` (also required by `/add-game`, `skin-designer` and `mobil-porter`): no per-frame allocations in `update`/`draw`, static art cached in offscreen canvases, event-driven scene parts (settled Tetris board, Arkanoid blocks) in a layer repainted only when a version counter changes, and frames skipped when nothing changed (Tetris skins expose the optional `isAnimating()`; if missing the engine always repaints). `GameScreen` creates the engine once, after `useHydrated()` (otherwise a stored non-default skin builds and discards one engine per reload). Measure on a production build with the CPU throttled 20× (normal speed is vsync-bound and shows nothing).
- Dev server gotcha: Turbopack's persistent cache (`.next/dev/cache/turbopack`) can serve stale CSS after editing `app/globals.css` (the page renders the new components with the old stylesheet). Stop `next dev`, delete that folder and restart; the first `npm run dev` after clearing it stops on an upgrade reminder, run it again.
- TypeScript is `strict`; ESLint extends `eslint-config-next` core-web-vitals + typescript.
