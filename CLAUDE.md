# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Arcade Vault: a retro platform to play games online and compete for the highest scores (README and UI in Spanish). The project follows spec-driven development: every feature has a spec in `specs/NN-slug.md` (01 visual screens, 02 home, 03 about/contact, 04 Supabase, 05 asteroids, 06 leaderboard and `games` table, 07 tetris, 08 arkanoid, 09 serpentina) and is implemented on a `spec-NN-slug` branch (`specs/.spec-config.yml`: `AutoCreateBranch: true`).

Commands: `npm run dev`, `npm run build`, `npm run lint`. No test runner is configured; changes are verified in the browser (Playwright MCP) against the spec's acceptance criteria.

## Architecture notes

- App Router only (`app/`); no `pages/`, no `src/`. Path alias `@/*` maps to the repo root. Routes: `/` (home, sections in `components/home/`), `/biblioteca` (library with category filter), `/juegos/[id]` (detail + leaderboard), `/juegos/[id]/jugar` (game player), `/salon` (hall of fame), `/acerca-de` (about + contact form), `/auth` (mock login). Page params use the global `PageProps<"/route">` type.
- `next.config.ts` enables `cacheComponents`, `partialPrefetching`, and `experimental.agentFeedback`. `cacheComponents` changes caching/dynamic-rendering semantics, so consult the docs before fetching data or using request APIs in components.
- Styling: Tailwind v4 wired through Turbopack (a `turbopack.rules` entry in `next.config.ts` runs `@tailwindcss/turbopack` on `*.css`), configured in CSS only (no `tailwind.config`). `app/globals.css` holds the retro theme ported from `references/templates`: tokens on `:root` (`--bg`, `--ink`, `--cyan`, `--magenta`, `--yellow`, `--green`, `--gold`...) exposed as utilities via `@theme inline` (`bg-bg-2`, `text-cyan`, `font-pixel`...), plus most component styles as plain classes (`av-*`, `crt`, `lb-*`...). Dark theme only (`color-scheme: dark`). The root layout loads `Press_Start_2P` and `JetBrains_Mono` via `next/font/google`, uses the global `LayoutProps<"/">` type, and wraps `Nav` + page + `Footer` in `SessionProvider`.
- Session: no Auth yet. `SessionProvider` (`components/session-provider.tsx`) is a mock stored in `localStorage` key `av_user` (`{ name }`), read with `useSyncExternalStore` (null on the server and during hydration, in-memory fallback if storage is blocked). `useSession()` exposes `user`, `login`, `signOut`.
- Contact form (`/acerca-de`): Client Component `components/about/contact-form.tsx` calls the Server Action `sendContactMessage` (`app/acerca-de/actions.ts`), which validates against `CONTACT_LIMITS` (`lib/contact.ts`), has a `website` honeypot, strips control chars from header fields, and sends via Resend. Needs `RESEND_API_KEY`, `CONTACT_TO_EMAIL`, `CONTACT_FROM_EMAIL` (see `.env.example`).
- Supabase clients live in `lib/supabase/`: `client.ts` (Client Components), `server.ts` (Server Components/Actions/Route Handlers, async, reads cookies) and `anon.ts` (no cookies, for `use cache`). Always call `createClient()` per request; never keep a client in a module-level constant or global. Config comes from `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (see `.env.example`); no secret/service_role key is used.
- Database (Supabase, schema in `supabase/migrations/`, applied with `apply_migration`): `games` (catalog, 8 rows, read-only) and `scores` (public read; public insert only with `is_seed = false`; no UPDATE/DELETE), plus view `game_stats` (`security_invoker`, `best`/`plays` per game) and functions `get_leaderboard` / `get_player_best` (best score per player name, case-insensitive). RLS is on in the same migration that creates each table. Scores are identified by player name, not user (no Auth), so anyone with the publishable key can insert any name; this is accepted until the Auth spec. Types are generated in `lib/supabase/database.types.ts` (regenerate after schema changes). The 50 `is_seed` rows cover 5 games (the 4 non-playable ones, `gloton`, `invasores`, `ranaria` and `duelo-pixel`, plus `tetris`, which kept the seeds of its former `caida` row); `asteroids`, `arkanoid` and `serpentina` only have real scores (`arkanoid` is the former `bloque-buster`, renamed by migration; the seeds of `arkanoid` and `serpentina` were deleted by migration because they were unreachable or would not be reached in normal play). The build needs `NEXT_PUBLIC_SUPABASE_*` because `generateStaticParams` reads `games`.
- Reads live in `lib/queries/`: `games.ts` (`getGames`/`getGame` are `use cache` with `cacheTag("games")` and long `cacheLife`; `getGamesWithStats` adds dynamic `game_stats`) and `scores.ts` (`getLeaderboard`, dynamic, never cached; dates formatted on the server in UTC/`es-ES`). Anything inside `use cache` must use `createAnonClient()` from `lib/supabase/anon.ts`; dynamic reads use the cookie-aware `server.ts` client under `<Suspense>`. Pages pass data to Client Components (`Library`, `HallOfFame`, `GameCard`) via props; "Tu mejor marca" is the only client-side query (`get_player_best` with the browser client, by session name). Shared game types (`Game`, `GameWithStats`, `CATS`, `formatPlays`, `PLAYABLE_GAME_IDS`) are in `lib/games.ts`.
- Saving scores: `GameScreen` calls the Server Action `saveScore` (`app/juegos/[id]/jugar/actions.ts`) once per game when `onHudChange` reports `gameover`, only with a session and score > 0 (guests see a link to `/auth`). `saveScore` validates against `lib/leaderboard.ts` limits and `PLAYABLE_GAME_IDS`, inserts, reads the rank with `get_player_best`, and `revalidatePath`s `/salon` and `/juegos/{id}`. It is not a security barrier (the DB `CHECK`s and RLS are). The status (`GUARDANDO` / `GUARDADO #N` / `ERROR` + `REINTENTAR`) is React in the CRT bottom bar; the engine is untouched.
- Game engines live in `lib/games/` (`types.ts` shared; one folder per game: `asteroids/`, `tetris/`, `arkanoid/`, `serpentina/`, each split into `constants`, `entities`, `utils`, `game` and optionally `levels`/`draw`). An engine is plain TypeScript with no React/Next imports: `createXGame(canvas, callbacks)` keeps all state in its closure and returns `{ pause, resume, restart, destroy }`; `destroy()` must cancel rAF and remove every listener. `components/game/game-screen.tsx` (Client Component) creates the engine in `useEffect`, returns `destroy` as cleanup, and mirrors the HUD via `onHudChange`. Per-game settings live in `GAMES_CONFIG` (game-screen): `create`, internal canvas `width`/`height` (asteroids, arkanoid and serpentina 800×600, tetris 300×600), `showLives` (false for tetris and serpentina, whose engines emit `lives: 0`) and `showNext`. With `showNext` the frame switches to the vertical `crt--side` layout and the engine reports the next piece through the optional `onNextChange` callback, which React draws on a second 120×120 canvas (the engine still receives a single canvas). Binary assets live in `public/games/<id>/` and the engine loads them itself (arkanoid loads its spritesheet before starting the loop and aborts if destroyed meanwhile). A game without a "win" status emits `gameover` when completed (arkanoid draws a victory overlay, serpentina one for a full board), so the score is saved like any other game. Serpentina uses no assets: everything is drawn on the canvas, with the static background (sky, hills, checkerboard) cached once in an offscreen canvas, and it moves on a 40×30 grid of 20 px cells by accumulating `dt` into fixed steps. To add a game (or use `/add-game`): new engine folder, register it in `GAMES_CONFIG` and in `PLAYABLE_GAME_IDS` (`lib/games.ts`), and make sure it has a row in `games` (insert or rename via migration).
- TypeScript is `strict`; ESLint extends `eslint-config-next` core-web-vitals + typescript.
